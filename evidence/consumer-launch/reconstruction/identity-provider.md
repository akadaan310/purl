# PURL Identity: provider evidence and implementation boundary

Observed **2026-10-18 16:28 UTC**. Scope: read-only provider research and isolated local tests for `02_IDENTITY.md`; no login, email, OAuth client creation, configuration change, secret retrieval, deployment, or commit. PURL code inspected at `d6fbc666890f85913fac3553be055a44cb9ec620`.

## Decision

**Supabase's established OAuth 2.1/OIDC server can support PURL Identity; the existing project is not enabled for it.** Keep this provider as the first option, subject to safely hosting its central consent UI. Build two independent OIDC relying parties and product authorization stores. Do not create an authorization server or treat the existing magic-link adapter as completed SSO. Supabase currently calls the OAuth server beta. [Official overview](https://supabase.com/docs/guides/auth/oauth-server), [setup](https://supabase.com/docs/guides/auth/oauth-server/getting-started)

The principal integration constraint is a **shared project Site URL**. Supabase combines that URL with an OAuth Authorization Path. The existing Site URL must be inspected without retrieving other configuration values, and preserved if another application uses it. Neither current documentation nor the inspected implementation provides an independent absolute consent UI URL. If the current Site URL's application cannot safely host `/oauth/consent`, use a dedicated identity project or an established external provider. Auth0 is a viable managed fallback, documented in [identity-alternative.md](identity-alternative.md); it introduces another issuer and account mapping work.

## Verified provider capabilities and limits

- **OIDC code flow:** Supabase issues short-lived, single-use authorization codes, PKCE-bound token exchanges, refresh tokens, and ID tokens when `openid` is requested. ID tokens require RS256 or ES256. The issuer is `https://frxufmwwbegconolevkw.supabase.co/auth/v1`; authorization, token, and UserInfo paths are `/oauth/authorize`, `/oauth/token`, and `/oauth/userinfo` under that issuer. [Flows](https://supabase.com/docs/guides/auth/oauth-server/oauth-flows)
- **Separate clients and SSO:** Register one client per product and environment. Central login/consent UI uses the same provider identity and central browser session; each product performs its own code flow and stores its own session. Signing into CGIT first can create the shared identity and later sign into PURLs without another identity account. Shared browser SSO requires that central UI/session; common credentials or two `supabase-js` local-storage sessions alone do not establish cross-origin SSO. Supabase handles codes and tokens; our UI handles login/consent with documented `getAuthorizationDetails`, `approveAuthorization`, and `denyAuthorization` methods. [Setup](https://supabase.com/docs/guides/auth/oauth-server/getting-started)
- **Verified email:** OIDC exposes the authoritative `email_verified` claim. Require it to be `true` after token validation, or require server-returned `email_confirmed_at` when using `/user`. A valid account ID is insufficient. Email is mutable; never key identity or merge accounts by email. Supabase's identity linking documentation describes protections for unverified identities; app-driven linking must prove ownership of both accounts. [Flows](https://supabase.com/docs/guides/auth/oauth-server/oauth-flows), [identity linking](https://supabase.com/docs/guides/auth/auth-identity-linking)
- **Scopes are limited:** Standard identity scopes are supported. Custom OAuth scopes are currently unsupported, and identity scopes do **not** restrict database access. OAuth access tokens otherwise have normal user access plus `client_id`. Product API scopes, ownership, quotas, consent, and artifact grants must be enforced in application authorization and, where appropriate, RLS using `client_id`. Do not advertise unsupported `purls:write` or `cgit:commit` provider scopes. [Token security](https://supabase.com/docs/guides/auth/oauth-server/token-security), [flows](https://supabase.com/docs/guides/auth/oauth-server/oauth-flows)
- **Revocation:** `supabase.auth.oauth.revokeGrant(clientId)` revokes that client's sessions/refresh tokens; documented `signOut` has explicit local/global scopes. Existing access JWTs can remain valid until expiry. Immediate protected-operation revocation requires a live session/credential check, not JWT verification alone. Provider deletion also does not automatically revoke detached product tokens. [OAuth grants](https://supabase.com/docs/guides/auth/oauth-server/oauth-flows#managing-oauth-grants), [sessions](https://supabase.com/docs/guides/auth/sessions), [signOut](https://supabase.com/docs/reference/javascript/auth-signout)
- **AI grants:** The OAuth server supports authorization-code and refresh grants, not `client_credentials` or resource-owner-password grants. A human's delegated OAuth grant is distinct from a provider-attested AI identity. [Flows](https://supabase.com/docs/guides/auth/oauth-server/oauth-flows)

The current changelog was fetched before this decision. Relevant changes include the 2025 OAuth server beta launch, a November 10, 2026 project-API TLS cipher change, and a platform `/v1/oauth/token` HTTP-status change. The platform token endpoint is separate from project `/auth/v1/oauth/token`; accept valid 2xx responses rather than assuming 201. No relevant documented change removes project OAuth/OIDC support. [Changelog](https://supabase.com/changelog), [TLS change](https://supabase.com/changelog/cbc-tls-ciphers-deprecated)

## Existing routes and observed security gaps

| Contract | Current implementation |
| --- | --- |
| `GET /api/auth/config` | Returns optional Supabase URL/public key and availability. Configuration presence does not mean OAuth is enabled. |
| `POST /api/auth/start` | Starts email OTP/magic link; validates email and caller-created browser state, redirects to `/workspace?auth_state=...`; no PKCE code exchange. |
| Browser callback | Reads `#access_token`, checks a one-use local-storage state intent with a ten-minute age bound, removes URL fragment, exchanges token for PURL token. This is the existing implicit-style magic-link path. |
| `POST /api/auth/session` | Accepts provider bearer token (or JSON `access_token`); calls `/user`; derives stable PURL principal from `(issuer,id)`; appends a random PURL token hash, retaining 50. Does not enforce verified email, client binding, consent, expiry, or provider revocation linkage. |
| `POST /api/session` | Creates a self-declared guest/human/agent/service and opaque PURL token. Client labels and requested identity kinds do not prove identity. |
| `GET /api/session` | Authenticates token hash and principal `revoked_at`; no credential expiry check. |
| UI disconnect | Clears this tab's session storage only; no server revocation or provider logout. |

Source: `/workspace/purl/service/auth.js`, `service/domain.js`, `service/domain/support.js`, `service/http.js`, `service/openapi.js`, `web/app.js`. Current OpenAPI omits the existing auth-config/start/session routes. No OIDC client, consent handler, product profile provisioning, account export/delete/recovery, or logout/revoke route is implemented in these inspected files.

Local verification command: `node --test test/product/auth.test.js test/product/domain.test.js test/product/http.test.js test/product/security-regression.test.js` → **78 passed, 0 failed, 0 skipped**. These establish existing behavior, not completed SSO. Covered conditions include provider absence fail-closed, ignored editable metadata, stable subject mapping, forged token rejection, hashed secret persistence, account isolation, URL credential rejection, cross-origin write rejection, and attenuating/revocable resource grants.

A separate **isolated in-memory mock probe** demonstrated four missing protections without accessing production: an unverified email received `identity_verified=true` with HTTP 201; a detached local token remained usable after a past `expires_at` was placed on its record; a provider-revoked session failed a new exchange (401) while its prior local token still worked (200); an agent session omitted supplied owner/expiry and stayed usable. These are implementation gaps, not claims of an exploit against live Supabase.

## Recommended product boundary and acceptance conditions

Use a maintained OIDC relying-party library for discovery, token exchange, nonce/audience/issuer validation, and JWKS handling. Products never mint OAuth codes or tokens. A central identity mapping owns immutable internal UUIDs keyed by validated `(iss,sub)`; each product owns its own handle/profile, resources, quotas, scopes, and authorization. Handle renames never change identity. Cross-product signup grants credential reuse; CGIT profile/namespace activation from PURLs requires explicit recorded opt-in and an idempotent provisioning operation. First signup in CGIT provisions its own profile; PURLs can provision its profile on the first subsequent authorized visit. No email-based auto-merge.

Each product BFF holds provider tokens server-side and gives its browser an origin-bound Secure, HttpOnly, SameSite cookie identifying a persisted, expiring, revocable session. Browser API calls use that BFF; do not try to keep browser-side Supabase token refresh working with inaccessible HttpOnly provider cookies. Cookie mutation endpoints need origin and CSRF checks. Keep API bearer credentials separate and constrained to product, principal, scopes, resource restrictions, and expiry. A valid PURLs credential is not sufficient authority to read CGIT artifacts.

Implement and test: both signup directions; opt-in and declined activation; retry-safe concurrent profile provisioning; duplicate identity signup; verified-email rejection; account-link proof; incorrect issuer/audience/nonce/state; replayed/expired codes and wrong PKCE verifier; redirect allowlists; expired/revoked local tokens and provider sessions; consent removal revoking product integrations; account isolation; cross-product artifact allow/deny; account export/delete and recovery; handle rename; resource and signup rate limits. Global account logout/delete must synchronously invalidate product sessions/delegations, then revoke provider grants/sessions; retries must be safe. Provider JWT revocation latency must be explicit and not bypass a product's immediate local revocation checks.

AI principals need their own immutable ID, owner ID, delegation chain, product/resource scopes, creation/expiry timestamps, revocation status, and a per-credential hash/identifier. Model/provider labels are unverified claims until separately attested; store attestation method, verifier, evidence, and expiry explicitly. Credentials must expire and be individually rotatable/revocable; owner, consent, or ancestor revocation must invalidate descendants at request time and worker commit time. Audit issued/delegated/refreshed/revoked/use events without raw secrets. Existing grant attenuation is reusable, while the current principal-wide hash array cannot express these session and AI credential lifecycle requirements.
