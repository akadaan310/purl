## Delivered behavior and API

The existing ResourceService constructor/export and handle/workOnce contracts remain. Proposals can suggest bounded source/state changes to a currently readable public resource, or an owned private resource. They do not mutate the resource. Only its authenticated owner with `resources:write` can explicitly accept or reject.

- POST `/api/resources/:id/propose` with `{expected_version,base_version?,summary?,source?,state?}` returns `{proposal}`, status 201. At least source or state is required. Optional `base_version` must equal the current resource version; `expected_version` always must match. `Idempotency-Key` binds the complete payload and proposer identity.
- GET `/api/resources/:id/proposals` returns `{items:[{proposal,decision}]}`. Owner sees all; another active principal sees only their own suggestions. GET `/api/resources/:id/proposals/:proposalId` returns `{proposal,decision:null|record}` to the owner or original proposer. Read credentials may carry `resources:read` or `resources:write`. Anonymous/foreign proposal reads are denied even when the resource is public.
- POST `/api/resources/:id/commit` with `{expected_version,proposal_id,decision:'accept'|'reject'}` returns `{resource,proposal,decision}`. Decision defaults to accept. Owner authorization is checked before replaying an idempotency receipt. The immutable proposal's exact `base_version` must match the current resource version for both acceptance and rejection. A stale proposal must be submitted again against the current version. Acceptance changes only its validated source/state; changed source increments source_revision and invalidates active_build. Rejection records the decision without applying proposed content. Both decisions advance resource history exactly once.

The native manifest now publishes these real input schemas, proposal-read link and bounds. Expired/invalid-expiry principals are not advertised as having mutation authority. Unverified guests with the proper resource scopes retain the explicitly intended preview capabilities.

## Persistence and authority

Proposal storage is in a server-derived, per-resource private shard `launch-resource-proposals:<resource-id>`, never in a caller-selected scope or one shared global index. Proposal rows carry resource ID, server-derived owner, proposer, exact base version, source/state, timestamp and immutable content digest. No mutation API rewrites them. The per-resource proposal counter, immutable proposal and proposer-namespaced command receipt commit atomically. Limits are 200 lifetime proposals per resource and 20 per proposer, subject to shared storage quotas. A duplicate idempotency key does not consume another slot.

Owner decisions live in the authenticated resource owner's scope. The decision, new resource state, immutable version, event and idempotency receipt commit together in one CAS transaction. Source/state are revalidated and the proposal digest is checked before applying. No body owner/scope/proposer is trusted. A proposal ID from another resource cannot select its storage namespace. GETs resolve the live resource owner/visibility first; changing a public resource to private removes a foreign proposer's access. Erasing its owner/resource makes these lookup paths unavailable.

Near-64-KiB source and state together exposed a full-response receipt exceeding the store's 256-KiB row limit. Decision receipts now atomically retain references to the immutable version/event/proposal/decision and reconstruct the identical original response for retries, rather than duplicating the combined content into one oversized receipt row. Other existing command-receipt formats remain supported.

## Validation and workers

`requireActor` now rejects missing, malformed, non-finite and expired expiry values. Source/state/input accept only persistable finite plain JSON: cycles, undefined values, custom prototypes, getters, sparse/decorated arrays, dangerous property names, NUL and malformed Unicode are rejected before clone/hash/write. JSON traversal is bounded to 64 levels and 100,000 nodes. Native source and state are each limited to 64 KiB; creation validates state, tests and schemas before reserving an address. Source compiles through the closed native compiler and only pure bounded plans are admitted. Authored JavaScript and external code execution remain disabled.

Execution authority is checked against the original owner, requested principal and live resource scope at claim and again immediately before publication. Missing/revoked/invalid-expiry authority cancels without an artifact. Output and complete execution data are validated and bounded before persistence. Existing lease token and CAS fencing prevent an expired/interrupted worker publishing after a replacement worker takes over. Only the closed pure interpreter's work is retried after lease expiry; no external/model side effect is introduced.

## Integration limits and remaining concerns

The shared store still applies 256-KiB rows, 32 changes/transaction, 10-MiB scopes and 4096 records per scope; these can be stricter than individual resource/component maxima. Proposal shards are bounded per resource and do not accumulate in a global 4096-key tenant. Existing per-resource address shards and legacy read-only fallback are preserved.

The new 64-KiB create-state bound also applies to mission seeds; a larger mission must be split into bounded resources rather than bypassing the state bound. A rejected stale proposal is deliberately not decided; resubmit against the current version. Owner/resource erasure denies subsequent proposal access, but this module does not implement a physical cross-shard garbage collector or claim past exports can be recalled. Root owns production retention/erasure policy and any physical shard cleanup. HTTP authentication/CSRF/response negotiation, deployment, production persistence checks, SDK/UI flows and the whole-project suite remain root work. No claim of verified human identity follows from guest capabilities, and hashes prove consistency rather than external truth.
